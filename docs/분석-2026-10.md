# telpo-server 분석 보고서

분석 기준: `kakao+tmap` 브랜치 (커밋 d10a8f6), 2026-10-18.
rea(`rea-agents`)는 JavaScript 앱 분석 도구라서 이 프로젝트(Java 21 / Spring Boot 4.1.1)에는 맞지 않아 쓰지 않았고, 소스 46개 파일을 직접 읽어 분석했습니다. `./gradlew compileJava`는 성공했습니다.

## 1. 무엇을 하는 서버인가

여행 계획 지도 서비스(`telpo-client`의 백엔드)용 REST API입니다. 로그인 없이 여행을 만들면 **편집 토큰**과 **공유 토큰**을 발급하고, 사용자는 장소를 검색해 일차별 일정에 담고, 정류지 사이 경로(자동차/도보/대중교통)와 추천 방문 순서를 받습니다.

- 장소 검색: 카카오 로컬 REST API
- 경로 계산: Tmap Open API (자동차·도보·대중교통 모두)
- 저장소: PostgreSQL 17 (docker-compose), JPA `ddl-auto: update`
- 가상 스레드 활성화

## 2. 구조

```
common/   LatLng, GlobalExceptionHandler, NotFoundException
map/      MapProvider(장소검색) / RouteProvider(경로) 인터페이스, Route·TransitLeg·DistanceMatrix
  kakao/  KakaoMapProvider
  tmap/   TmapRouteProvider (+ 30분 TTL·500건 LRU 메모리 캐시)
place/    Place 엔티티(provider + providerPlaceId 유니크), 검색 API, resolveOrCreate
route/    RouteController/Service, RouteOptimizer(최근접 이웃 + 2-opt)
trip/     Trip/TripStop 엔티티, 토큰 발급(SHA-256 해시 저장), 생성/조회/저장 API
```

프로바이더를 인터페이스로 분리해 해외 확장(Google 등) 시 교체할 수 있게 설계되어 있습니다. 계층 분리는 깔끔한 편입니다.

## 3. 주요 기능 (API)

| 메서드 | 경로 | 내용 |
|---|---|---|
| POST | `/api/trips` | 여행 생성, editToken(원문은 이때만 노출)·shareToken 발급 |
| GET | `/api/trips/edit/{editToken}` | 편집용 조회 |
| GET | `/api/trips/share/{shareToken}` | 읽기 전용 조회 |
| PUT | `/api/trips/edit/{editToken}` | 자동 저장: 제목·날짜·전체 정류지를 통째로 교체 |
| GET | `/api/places/search?q=&lat=&lng=` | 카카오 키워드 검색 |
| POST | `/api/routes` | 경유지+이동수단 → 경로선·거리·시간·택시/통행료/대중교통 요금·구간 |
| POST | `/api/routes/optimize` | 장소 목록 → 추천 방문 순서 |

## 4. 눈에 띄는 문제 (중요도 순)

### 높음
1. **경로 최적화 호출 수 제한 없음** — `OptimizeRequest`(`route/dto/OptimizeRequest.java`)에 최대 개수가 없고 `TmapRouteProvider.getMatrix`가 N×(N−1)번 Tmap을 호출합니다. 점 32개 한 번이면 992건으로 무료 한도(1,000건/일)가 끝납니다. 인증·레이트리밋도 없어 누구나 반복 호출할 수 있습니다. `@Size(max=…)`와 간단한 레이트리밋을 권장합니다.
2. **공유 Place 데이터를 클라이언트가 오염시킬 수 있음** — `PUT /edit` 요청의 장소명·좌표·provider·providerPlaceId를 그대로 믿고 `PlaceService.resolveOrCreate`가 (provider, providerPlaceId) 기준으로 처음 저장된 값을 모든 여행이 재사용합니다. 누군가 `KAKAO`/실제 장소 ID에 가짜 이름·좌표를 먼저 넣으면 이후 다른 사용자의 여행에도 그 값이 보입니다(코드 흐름상 추론, 실행 확인은 안 함).
3. **최적화의 출발점이 고정되지 않음** — `RouteOptimizer.twoOpt`가 `i = 0`부터 구간을 뒤집어 첫 지점(보통 숙소/출발지)이 중간으로 옮겨질 수 있습니다. 의도라면 문서화, 아니라면 `i`를 1부터 시작해야 합니다. 또 자동차 소요시간은 비대칭인데 2-opt 비용 계산은 뒤집힌 내부 구간 비용 변화를 무시해서, 결과가 실제로 더 나빠지거나 이론상 개선 루프가 끝나지 않을 수 있습니다(추론).

### 중간
4. **예외가 500으로 새는 경우들** — `GlobalExceptionHandler`가 다루지 않는 예외:
   - `TMAP_APP_KEY` 없음, 경유지 < 2 → `IllegalStateException`/`IllegalArgumentException` → 500
   - `countryCode`가 `@NotBlank`만 있고 DB 컬럼은 길이 2라 `"KOR"` 등이 오면 DB 오류 → 500
   - 같은 장소를 동시에 저장하면 유니크 제약 위반(`DataIntegrityViolationException`) → 500
   - 요청 JSON 형식 오류(`HttpMessageNotReadableException`), 잘못된 `mode` 값 등은 Spring 기본 응답
5. **자동차 경유지 개수 검증 없음** — Tmap `passList`는 최대 5개인데 검증이 없어 경유지 8개 이상이면 Tmap 4xx → 일반적인 502만 받습니다.
6. **외부 API 타임아웃 미설정** — Kakao/Tmap `RestClient`에 connect/read 타임아웃이 없어 상대가 멈추면 요청이 오래 묶입니다.
7. **입력 검증 부족** — 위경도 범위, `startDate ≤ endDate`, `dayNo`/`orderNo` 양수·중복, 정류지 개수 상한이 없습니다. `UpdateTripStopRequest.lat/lng`가 원시 `double`이라 빠지면 0,0으로 저장됩니다.
8. **CORS 설정 없음** — 프론트가 다른 오리진에서 직접 호출한다면 막힙니다(프록시를 쓰면 무관).

### 낮음
9. **테스트가 사실상 없음** — `contextLoads` 하나뿐이고 실제 PostgreSQL이 필요해 DB 없이 `./gradlew build`가 실패합니다. `RouteOptimizer`, `TmapRouteProvider` 파싱은 단위 테스트하기 좋은 대상입니다.
10. **운영 전환 시 점검** — `ddl-auto: update`(마이그레이션 도구 없음), `com.telpo.server` 로그 레벨 `debug`, 편집 토큰이 URL 경로에 있어 접근 로그·프록시 로그에 남을 수 있음.
11. Kakao 키가 비어 있으면 `"KakaoAK "` 헤더로 호출해 401 → 502가 되는데, Tmap은 미리 검사해 500을 냅니다. 둘 다 같은 방식(시작 시 검사 또는 503)으로 맞추면 좋습니다.

## 5. 잘 된 점
- editToken은 SHA-256 해시만 저장, 256비트 난수 토큰, 원문은 생성 응답에서만 노출
- API 키는 서버 환경변수로만 관리, `.env`는 gitignore 처리 확인
- 외부 API 실패 상세는 로그에만 남기고 클라이언트엔 일반 메시지
- 대중교통 "너무 가까움(코드 11)"을 도보로 대체, 구간별 path 인덱스 제공 등 프론트 배려가 세심함
- `open-in-view: false`, 엔티티 보호 생성자 등 JPA 기본기 양호
